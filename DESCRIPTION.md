# HERMES-CONSOLE — что это, зачем и как устроено

## 1. Зачем этот проект

Когда ИИ-агент (Hermes) работает на чужом Windows-сервере, обычно всё происходит
невидимо: SSH-команды уходят в неинтерактивную сессию, и человек у монитора не видит
ничего. Это плохо: нельзя проконтролировать, что именно делает агент, нельзя поймать
ошибку глазами, нет доверия.

**HERMES-CONSOLE решает это одной идеей:** на рабочем столе сервера (сессия 1, там же,
где пользователь) открывается **настоящее окно `cmd.exe`**, и агент управляет им не
«из-под земли», а **реальными нажатиями клавиш** — каждый символ, каждая команда и весь
вывод видны на мониторе вживую. Пользователь может в любой момент посмотреть, что делает
агент, а агент может читать то, что происходит в окне, и отвечать на основе этого.

Три принципа, на которых держится весь проект (сформулированы владельцем сервера):

1. **Строго визуально, без фоновых режимов.** Никаких скрытых шеллов и psexec — только
   видимое окно, которым управляет агент.
2. **Мост надёжен как скала.** Окно консоли и статус агента не должны «зависать» и врать:
   трей-иконка у часов всегда честно показывает, жив ли мост, занят ли он, работает ли агент.
3. **Как будто ничего не случилось.** Если мост всё же упал и был поднят заново, новое окно
   обязано показать предыдущую историю команд — пользователь не должен терять контекст.

## 2. Общая архитектура

```
┌─────────────── Mac (у пользователя) ───────────────┐
│  hermes_console_client.py   ← агент вызывает его   │
│        │  TCP 127.0.0.1:18799                      │
│        ▼                                           │
│  SSH-туннель (ssh -L 18799:127.0.0.1:18799)        │
└────────┼───────────────────────────────────────────┘
         │  Tailscale-сеть
         ▼
┌─────────────── Windows-сервер (сессия 1) ──────────┐
│  127.0.0.1:18799 ← hermes_bridge.ps1 («мост»)      │
│        │                                           │
│        ├─ WriteConsoleInput  → печатает клавиши    │
│        │   в реальную консоль (их видно на экране) │
│        ├─ ReadConsoleOutput  → читает экран и      │
│        │   весь скроллбэк буфера                  │
│        └─ дочерний cmd.exe   ← сама видимая консоль│
│                                                    │
│  hermes_tray.ps1 («трей» у часов)                  │
│        ├─ иконка-светофор: честный статус моста    │
│        ├─ воркер: следит за мостом, перезапускает  │
│        └─ меню: Показать / Скрыть / Перезапуск /   │
│           Выход (решает пользователь)              │
└────────────────────────────────────────────────────┘
```

Ключевое: мост слушает **только** `127.0.0.1:18799` — снаружи сервера порт недоступен
физически, попасть в него можно только через SSH-туннель. Туннель и мост — всегда один
юнит: их поднимает и роняет один скрипт (`console_up.sh` / `console_down.sh`).

## 3. Компоненты: что именно делает каждый файл

### `hermes_bridge.ps1` — мост (сердце проекта)

Один PowerShell-процесс, который **владеет** окном консоли и делает пять вещей:

| Блок | Логика |
|---|---|
| **Сетевой сервер** | Слушает `127.0.0.1:18799`, читает JSON-запросы по протоколу v2 (см. §4), на каждый запрос отвечает ровно один блок `RES…` + `DONE…`. Весь обработчик соединения завёрнут в `try/catch`: обрыв клиента не убивает мост. |
| **Инжект клавиш** | `WriteConsoleInput` в буфер ввода консоли:cmd.exe. Это не эмуляция и не SendKeys — символы попадают в ту же консоль, что и с физической клавиатуры, и их видно на экране. Спецсимволы: `\r` Enter, `\b`, `\t`, `\u0003` Ctrl+C, `\u001b` Esc. |
| **Чтение экрана** | `ReadConsoleOutputCharacterW`: `screen` — видимая область, `history` — весь скроллбэк (буфер 9999 строк). В конце всегда техническая строка `CURSOR x y SIZE wxh WINDOW WxH ATTR 0xNN` — по ней проверяются факты о буфере, окне и цветах, не глядя на монитор. |
| **Владение окном** | Мост сам показывает/прячет своё окно (`show`/`hide`), сам настраивает его внешний вид при старте и сам запрещает закрытие крестиком. Трей никогда не ищет окно по заголовку — только команды через TCP. |
| **Хранение истории** | После каждой рабочей операции скроллбэк (400 последних строк) пишется в `E:\LOCAL_HERMES\hermes_history.txt`. При старте моста, если файл есть, история **проигрывается в новый буфер** через `WriteConsoleW` с позиции (0,0) — без эха и без исполнения. Команда `cls` выполняется только при совсем первой установке. |

Порядок настройки окна при старте (важен — проверено на этом conhost):

1. `SW_SHOW` (скрытое окно не даёт менять шрифт — API виснет)
2. окно `87×16` → буфер `87×9999` → окно `87×16` (буфер обязан быть больше окна)
3. шрифт `Lucida Console 6×10 px`
4. позиция левого верхнего угла **жёстко 1366×844** (с зажимом внутрь виртуального экрана —
   работает на любой раскладке мониторов)
5. `SW_HIDE` (окно скрыто, пока пользователь не откроет его из трея)
6. через 1.5 с: напечатать `color 1f` (белый по синему; на этом conhost цветовые API
   `Get/SetConsoleScreenBufferInfoEx` возвращают false — проверено зондом, поэтому цвета
   ставятся штатной командой cmd), затем `cls` или восстановление истории.

`LockClose()`: из системного меню окна удаляется `SC_CLOSE` — крестик и Alt+F4 мертвы.
Смысл: закрытие окна убивает conhost, а с ним мост и всю историю. Закрывать можно только
через трей (Скрыть / Выход). Проверка факта: op `sysmenu` → `3` = закрытия нет в меню.

### `hermes_tray.ps1` — трей-апплет у часов

Двухпоточная конструкция, и в этом весь смысл:

- **UI-поток** (STA): иконка `NotifyIcon`, контекстное меню, таймер 500 мс для мигания.
  Он **никогда не трогает сокеты** — только читает кэш состояния. Это исправление
  реального бага: когда сеть была в UI-потоке, открытие меню мышкой вешало весь трей.
- **Воркер** (отдельный runspace): опрашивает мост (`hb`, таймаут 2.5 с, цикл ~0.8 с),
  ведёт счётчик неудач, перезапускает мост, исполняет команды из меню.

Обработчики меню **только кладут команду в очередь** (`ConcurrentQueue`) — меню закрывается
мгновенно, воркер делает дело после своего цикла.

#### Иконка-светофор: машина состояний

Состояние моста определяется по ответу на `hb` (`pong <сек> <opCount> <VISIBLE|HIDDEN>`):

| Иконка | Когда | Смысл |
|---|---|---|
| 🟠 Оранжевая | мост жив, агент не работает | готов, ждёт |
| 🟢 Зелёная мигает | `opCount` моста вырос (была рабочая операция) | агент работает; **2 вспышки на операцию** (правило владельца) |
| 🟡 Жёлтая | процесс моста **жив**, но 4+ опроса молчит | мост занят долгой командой или стартует; **это НЕ падение** |
| 🔴 Красная | процесс моста **умер** | воркер перезапускает его (не чаще раза в 30 с) |

Главное правило: **иконка не врёт.** Раньше занятый мост показывался красным — это было
ложью, потому что живой процесс воркер намеренно не трогает (иначе получался шторм
перезапусков живого моста). Теперь «жив, но молчит» = жёлтый BUSY, красный = только
реальная смерть процесса.

Дополнительно: счётчик `opCount` ведёт сам мост и считает **только рабочие операции**
(`keys`, `screen`, `history`, `show`, `hide`, `state`); опросы трея (`hb`, `ping`) не
считаются — иначе иконка мигала бы вечно. Если UI-поток запоздал с тиком больше чем на
1.6 с, воркер пишет в лог `UI STALL <мс>` — так деградация интерфейса фиксируется фактом,
а не ощущениями.

Единственность: мьютекс `HERMES-CONSOLE-TRAY` — второй экземпляр трея не поднимется.

### `hermes_console_client.py` — клиент с Mac

Тонкий, намеренно: ~50 строк, только stdlib. Отправляет один запрос, читает до `DONE`,
печатаёт полезную часть. Команды: `ping`, `hb`, `state`, `screen`, `history [N]`,
`keys "<текст>"`, `show`, `hide`, `quit`.

Важная эволюция: у `keys` **был** параметр `wait` (мост спал N мс и возвращал экран). Он
**удалён полностью** — см. §5.1. Теперь после долгой команды агент опрашивает
`screen`/`history` повторно.

### `console_up.sh` / `console_down.sh` — жизнь связки

`up` (идемпотентен, это обязательная точка входа):
1. Проверка SSH (по хостнейму сервера; при отказе — диагностика маршрута: Tailscale vs VPN).
2. Регистрация планировщика: задача `HERMES-CONSOLE` запускает **трей напрямую**
   (не через .bat: планировщик убивает всю job-объект когда действие завершилось — bat,
   вернувшийся мгновенно через `start`, утаскивал трей за собой).
3. Если порт слушает, но `ping` не отвечает — это **зомби** (мост умер, а сирота-cmd.exe
   унаследовал слушающий сокет): скрипт убивает процессы по совпадению командной строки,
   чистит сирот и поднимает заново.
4. Туннель: поднимается/переподнимается, только если локальный порт не слушает.
5. Сквозная проверка `ping` с ретраями (мост стартует 2–5 с из-за Add-Type).

`down` (парный разбор): `quit` мосту → убийство трея и моста по CommandLine →
сброс туннеля. Оба конца умирают вместе — «никогда не оставляй мост слушать после задачи».

### `hermes_console.bat` — ручной запуск

Двойной клик на сервере: стартует тот же трей. Нужен только для ручного восстановления;
штатный путь — `console_up.sh`.

## 4. Протокол v2

Строки без уникального префикса мост игнорирует — мусор в потоке не может быть принят
за команду (требование владельца: префиксы «заведомо уникальные, чтобы не путать»):

```
запрос   →  HERMES-REQ-8F27:{"op":"keys","text":"dir\r"}
ответ    ←  HERMES-RES-8F27:<строка1>   (повторяется N раз)
конец    ←  HERMES-DONE-8F27:keys       (ровно один; нет DONE — мост нездоров)
```

| op | Что делает | Ответ |
|---|---|---|
| `ping` | жив ли мост | `pong` |
| `hb` | здоровье + активность + видимость одним запросом | `pong <сек с последней работы> <opCount> <VISIBLE\|HIDDEN>` |
| `state` | видно ли окно | `VISIBLE` / `HIDDEN` |
| `screen` | видимая область экрана | строки + трейлер `CURSOR …` |
| `history {lines}` | весь скроллбэк | строки + трейлер |
| `keys {text}` | инжект клавиш, **мгновенно** | экран сразу после инжекта |
| `show` / `hide` | показать/спрятать окно (и переутвердить позицию) | `shown POS …` / `hidden` |
| `activity` | секунды с последней рабочей операции | `-1` если не было |
| `sysmenu` | проверка блокировки крестика | `3`=нет в меню, `2`=серое, `0`=закрываемо |
| `quit` | сохранить историю, убить cmd, закрыть мост | `bye` |

## 5. Логика, заложенная в код (правила и почему именно так)

### 5.1. Мост никогда не спит

Самый дорогой урок проекта. Мост однопоточный: если он сам спит (старый `keys wait=…`),
на это время глохнет всё — `hb` трея, клиент, статус. Одна команда с `wait` на 590 секунд
выглядела для пользователя как «мост упал и не восстанавливается», хотя процесс был жив.
Поэтому: `keys` = инжект + ответ за миллисекунды; ожидание долгих команд — повторным
опросом `screen`. Проверено фактами: `keys "ping -n 12 …"` вернулся за 0.08 с, и `hb`
ответил **во время** этой 12-секундной команды.

### 5.2. Живой процесс неприкосновенен

Воркер трея не убивает и не перезапускает мост, пока тот жив: «занят или стартует — не
трогаем» (иначе живой мост, владеющий портом, порождает шторм перезапусков). Смерть
констатируется только когда процесса нет — и тогда перезапуск с грейсом 30 с.

### 5.3. История переживает смерть моста

Скроллбэк буфера живёт, пока жив conhost. therefore мост копирует его на диск после каждой
операции (rolling 400 строк ≈ 25 экранов). При перезапуске история печатается прямо в
новый буфер (`WriteConsoleW` — это запись в экранную память, а не ввод: ничего не
исполняется, нет эха). Пользователь видит прежнее состояние окна «как будто ничего не
случилось». SQLite сознательно не использован: в PowerShell его нет из коробки, а
текстовый файл переживает любой краш и читается одной строкой.

### 5.4. Окно защищено от случайного закрытия

Крестик убивал conhost → мост → историю (это был реальный источник «исчезнувших записей»
в тестах, а не сетевые ошибки). Поэтому `SC_CLOSE` удалён из меню окна, закрытие — только
через трей. Буфер 9999 строк, окно 16 — записи не выматываются скроллом.

### 5.5. Всё проверяемо по факту, а не «на глаз»

Каждая настройка оставляет цифровой след: трейлер `CURSOR … SIZE … WINDOW … ATTR …`
в любом чтении экрана, `sysmenu` для крестика, `POS 1366x844 (555x199px)` в логе старта и
в ответе `show`, `hist-restore: replayed N lines` в логе, `UI STALL` при подвисании UI,
`bridge back after N failed polls` при восстановлении. Правило проекта: сначала факт из
лога/ответа, потом вывод.


### 5.6. Глубокий аудит кода перед публикацией

Перед пушем весь код прошёл проверку: `pyflakes` (клиент), `bash -n` (up/down),
парсер PowerShell 5.1 (`Parser::ParseFile`) на обоих .ps1 — 0 ошибок. Из ревью
исправлено: мёртвый C# цветовой API удалён (этот conhost ломает его на Get —
цвета только через `color 1f`); параметры `history` клампятся 1..9999 (бросок
внутри обработчика обрываёт ответ клиенту); клиент печатает одну понятную строку
`ERROR: cannot reach bridge at HOST:PORT` вместо трейса сокетов и валидирует
`--port`/`history LINES`; `!setep` отвергает порты вне 1–65535; воркер трея
опускает очередь даже после сигнала остановки (иначе `!quit` из шва осиротил бы
мост); после смены эндпоинта и рестарта воркер не спит между опросами — иконка
говорит правду за ~1 с. Логи трея и моста ротируются при старте (>1 МБ → `.log.old`).
UX: в меню живая строка состояния — `Console: VISIBLE on the monitor / HIDDEN
(double-click the icon to open) / bridge DOWN / starting...` — видно, открыто ли
окно, не открывая его.

## 6. Жизненный цикл (шпаргалка)

```bash
bash scripts/console_up.sh                      # поднять связку (идемпотентно)
python3 scripts/hermes_console_client.py hb     # здоровье: pong <сек> <ops> <VISIBLE|HIDDEN>
python3 scripts/hermes_console_client.py keys "dir E:\AI"   # мгновенный инжект
python3 scripts/hermes_console_client.py history 200        # скроллбэк
bash scripts/console_down.sh                    # уронить связку целиком
```

## 8. Подключение на новом сервере (конфигурация вместо правок кода)

Хост, порт и способ туннелирования — настраиваемые, код править не нужно.

**Со стороны клиента (Mac/Linux):** `scripts/console.cfg` (шаблон `console.cfg.example`, сам файл в `.gitignore`):

| Ключ | Значение |
|---|---|
| `HOST` | SSH-цель сервера (`user@адрес`) — только для up/down, клиенту её передавать нельзя |
| `KEY` | путь к приватному SSH-ключу |
| `PORT` | TCP-порт моста (он же конец туннеля) |
| `TUNNEL` | `ssh` (по умолчанию: сам поднимает `ssh -L`) или **`none`** — туннель реализован иначе (cloudflared, Tailscale serve, socat, открытый порт): ssh -L не поднимается вообще |
| `HC_HOST` | адрес, по которому мост доступен с ЭТОЙ машины (при `TUNNEL=none` — адрес вашего туннеля) |
| `EXPECT_HOST` | опциональная проверка идентичности сервера; пусто = пропуск |
| `PS1_DIR` | папка на сервере с .ps1-скриптами |

Клиент дополнительно принимает `--host H --port P` и переменные `HC_HOST`/`HC_PORT`.

**На сервере:** `hermes_console.cfg` рядом со скриптами (шаблон `hermes_console.cfg.example`) —
`BIND` (адрес прослушивания моста; по умолчанию loopback, можно указать Tailscale/LAN-адрес,
если туннель не приходит на loopback), `PORT`, `WORKDIR`, `BRIDGE_BIND` (адрес, куда трей
подключается к мосту). Приоритет: переменные окружения `HERMES_*` > файл > значения по умолчанию.

Все пути внутри .ps1 (логи, история, соседние скрипты) считаются относительно папки скриптов —
разворачивать можно в любую папку. Деплой: скопировать `scripts/*.ps1` с конвертацией LF→CRLF
(`sed 's/$/\r/'`) и запустить `hermes_console.bat` (или зарегистрировать задачу через up-скрипт).

**Endpoint прямо из трея (без файлов):** в контекстном меню трея есть раздел **Endpoint**:
метка текущего `host:port` (дублируется в тултипе иконки), пункт **«Auto-detect on this PC»** и
пункт **«Set host:port manually...»** (диалог host + port). Автоскан собирает кандидатов — сначала
сокеты, принадлежащие процессу `hermes_bridge.ps1`, затем остальные локальные слушатели (≥1024,
до 40), и проверяет каждого честным протокольным пробом `hb`: эндпоинтом считается только тот,
кто ответил `pong` (просто открытый порт — нет; так скан не путает мост с любым другим софтом).
Найденный или введённый вручную адрес применяется мгновенно (воркер переподключается) и
сохраняется в `hermes_console.cfg` (`BIND=`/`PORT=`) — чтобы после авторестарта мост слушал там же.
Вся сетевая работа — в воркере; UI-поток только кладёт команду в очередь, меню не зависает.
Ручной обходной путь без кликов: одна строка (`!detect` или `!setep <host> <port>`) в файл
`tray_cmd.txt` рядом со скриптами — воркер подхватывает её за цикл.

**Как пользователь узнаёт результат (v3.2):** в меню НЕТ строк-подсказок и строки статуса
(`Console: hidden` и `found: ...` убраны по требованию юзера) — меню содержит только действия.
Результат автодетекта/ручного ввода приходит **всплывающим уведомлением Windows у часов**:
«address applied» с полным адресом (найден и применён автоматически) или «nothing found»
(ни один локальный адрес не ответил протоколу). Если адресов, отвечающих протоколу, несколько —
воркер не гадает: UI-поток открывает **окно выбора**, где юзер кликом (или двойным кликом)
выбирает нужный адрес; выбор уходит воркеру командой `!pick <host> <port>` и применяется как
обычный эндпоинт (переподключение + запись в `hermes_console.cfg`). Сам диалог — чистый WinForms
на UI-потоке, сетью не занимается; его модальность не создаёт `UI STALL`, потому что воркер
продолжает опрашивать мост в своём runspace.

**Папка по умолчанию (v3.3):** раньше `WORKDIR` можно было менять только правкой
`hermes_console.cfg`. Теперь в контекстном меню трея есть раздел **Folder**: неактивная метка
текущей папки и пункт **«Set default folder...»** — нативный диалог выбора папок Windows
(FolderBrowserDialog, стартует с текущей папки). Это чистый UI: он только возвращает путь и
кладёт в очередь воркера `!setwd <путь>`. Воркер делает всё остальное: проверяет, что путь не
файл (иначе честное balloon-предупреждение и никаких изменений), пишет `WORKDIR=` в
`hermes_console.cfg` через тот же универсальный upsert, что и эндпоинт, и запускает авторестарт
моста — новый мост читает cfg и стартует `cmd.exe` в новой папке (несуществующая папка создаётся
им же, как и раньше). История консоли от смены папки не зависит: файл истории привязан к папке
скриптов, а не к `WORKDIR`, так что перезапуск «как будто ничего не случилось» сохраняется.
Папка показана в тултипе иконки и в меню; чтобы тултип не врал после ручной правки cfg или
чужого перезапуска моста, воркер каждые ~15 heartbeat-циклов спрашивает фактическую папку у
самого моста (оп `wd`, он же доступен клиентом как `hermes_console_client.py wd`).
Обходной путь без кликов: `!setwd <путь>` в `tray_cmd.txt`.
